# SSE 通信设计

SSE 通信分为两层：
- SSE协议解析
- 聊天业务事件解析

## SSE 协议解析

这是一个通用的 SSE 解析器，把 ReadableStream 字节流解析成标准的 SSE 消息。

```ts
type SSEMessage = {
  event: string;
  data: string;
  id?: string;
};

async function* parseSSE(
  stream: ReadableStream<Uint8Array>
): AsyncGenerator<SSEMessage>
```

它只负责协议，不关心聊天业务：
- 用 TextDecoder 以流式方式解码
- 保留上一次未处理完的字符和行
- 处理一个网络 chunk 中包含多个事件
- 处理一个事件被拆到多个 chunk
- 支持 \n\n、\r\n\r\n、\r\r 分隔
- 解析 event:、data:、id: 字段
- 多条 data: 按规范用换行连接
- 空行代表一个事件结束
- 忽略以 : 开头的注释行，便于以后支持心跳
- 忽略未知字段
- 没有 event 时使用默认事件名 message

因为流式响应本来就是分块到达的，字符串可能在字段值、JSON、甚至一个中文字符的 UTF-8 字节中间被截断。

## 聊天事件类型

在通用解析器之上，定义业务事件联合类型：

```ts
type ChatEvent =
  | { type: "delta"; text: string }
  | { type: "done" }
  | { type: "error"; message: string };
```

然后实现：

```ts
function parseChatEvent(message: SSEMessage): ChatEvent | null
```

它负责：
- 对 data 执行 JSON.parse
- 检查事件名和数据结构是否匹配
- 将后端格式转换成为前端好用的 ChatEvent
- 对未知事件选择忽略，保持向前兼容
- 对格式损坏的事件抛出明确的协议错误

## 发起聊天流

提供一个高层函数：

```ts
async function* streamChat(
  message: string,
  options?: { signal?: AbortSignal }
): AsyncGenerator<ChatEvent>
```

它负责：
- POST ${NEXT_PUBLIC_BACKEND_URL}/chat
- 设置 Content-Type: application/json
- 设置 Accept: text/event-stream
- 传入 JSON.stringify({ message })
- 传递 AbortSignal
- 检查 response.ok
- 检查 Content-Type 是否为 text/event-stream
- 获取 response.body
- 调用通用 SSE 解析器
- 调用聊天事件解析器

使用异步生成器，因为调用方可以很自然地消费：
```ts
for await (const event of streamChat(text, { signal })) {
  if (event.type === "delta") {
    // 追加文本
  } else if (event.type === "done") {
    // 结束回答
  } else if (event.type === "error") {
    // 展示后端流中的错误
  }
}
```

生命周期

一次请求应覆盖这些结束路径：
1. 收到 done
2. 收到 error
3. 网络异常
4. 非 2xx HTTP 响应
5. JSON 或事件格式错误
6. 用户主动取消
7. 流意外结束，但没有收到 done

最后一种应视为异常，因为当前后端正常结束时会明确发送 done。
必须考虑的边界情况

- 中文被拆在两个网络 chunk 之间
- 一个事件 JSON 被拆成几段
- 一次读取到多个完整事件
- CRLF 和 LF 混用
- 收到注释行或未知字段
- response.body 为 null
- 后端在开始流之前返回 502 JSON 错误
- 用户离开页面或发起新问题时取消旧请求
- 收到 done 后停止继续读取
- 增量文本必须“追加”，不能每次用新 delta 覆盖当前回答

## 暂不实现的功能

当前不需要在 sse.ts 中自动重连。原生 EventSource 会自动重连，但你使用的是带 JSON 请求体的 fetch，而且模型生成过程一旦重试，可能产生重复文本并增加模型费用。
如果未来需要断点续传，再增加：
- 后端为每个事件发送 id:
- 前端保存最后一个事件 ID
- 重连时发送 Last-Event-ID
- 后端支持从对应位置恢复
现阶段只需提供 AbortSignal，让用户主动停止或取消旧请求。
