## LLM消息结构

LLM 本身没有一个跨请求自动保存的“对话对象”。所谓多轮聊天，是每次把相关的 messages 数组重新发送给模型。

| role | 谁产生 | 作用 |
| --- | --- | --- |
| `system` | 后端或应用开发者 | 定义身份、安全边界、回答风格和输出格式 |
| `user` | 终端用户 | 当前问题或历史中用户之前说过的话 |
| `assistant` | 之前轮次的大模型 | 提供历史回答，让后续回答理解上下文 |
| `tool` | 后端工具系统 | 工具执行结果，例如天气查询、搜索结果、数据库记录 |

system: 消息通常只有一条，必须放在最前面。它决定模型的长期行为，由后端控制，前端不能直接覆盖

```json
{
  "role": "system",
  "content": "你是 DevPilot 的代码审查助手。按 P0、P1、P2 输出问题，并给出最小修复方案。"
}
```

user: 用户当前输入

```json
{
  "role": "user",
  "content": "审查这段代码：每个 token 都直接调用 setState。"
}
```

历史中之前用户的输入也会作为 user 再次发送

assistant: 上一轮模型的完整回答

```json
{
  "role": "assistant",
  "content": "P1：高频调用 setState 会导致大量 React 渲染。建议使用 requestAnimationFrame 合并更新。"
}
```

assistant 不只是展示记录，它告诉模型：“这是我之前说过的话，请在此基础上继续。”
一般只回传正常完成的 assistant 内容。流式生成到一半失败的内容是否回传，需要明确策略；通常不要当作正常的完整历史。

tool: 工具结果不是用户说出来的，也不是模型凭记忆生成的，而是系统实际执行工具后得到的数据。

概念上的工具调用顺序是：

```plain text
assistant 请求调用 get_weather
  -> 后端执行 get_weather
  -> tool 返回天气结果
  -> assistant 基于工具结果生成最终回答
```

```json
{
  "role": "tool",
  "tool_call_id": "call_weather_123",
  "content": "{\"city\":\"北京\",\"condition\":\"晴\",\"temperature\":\"24°C\"}"
}
```

标准 OpenAI-compatible Tool Calling 通常要求：

1. assistant 消息带 tool_calls。
2. 后端实际执行对应工具。
3. tool 消息通过 tool_call_id 关联那次调用。
4. 模型再生成最终回答。

tool 消息不能随便孤立插入，因为模型需要知道它对应哪个工具调用。

### 完整 messages 示例

下面是一个完整的“用户查天气并继续追问”的 OpenAI-compatible 消息列表示例。消息以 `user` 结束，可以直接发送给模型生成下一轮回答。

```json
[
  {
    "role": "system",
    "content": "你是 DevPilot 天气助手。回答必须简洁、准确，并使用中文。涉及实时天气时只能使用工具返回的数据，不能编造。"
  },
  {
    "role": "user",
    "content": "北京今天天气怎么样？适合跑步吗？"
  },
  {
    "role": "assistant",
    "content": null,
    "tool_calls": [
      {
        "id": "call_weather_001",
        "type": "function",
        "function": {
          "name": "get_weather",
          "arguments": "{\"city\":\"北京\",\"date\":\"今天\"}"
        }
      }
    ]
  },
  {
    "role": "tool",
    "tool_call_id": "call_weather_001",
    "content": "{\"city\":\"北京\",\"condition\":\"晴间多云\",\"temperature\":\"24°C\",\"humidity\":\"48%\",\"wind\":\"东北风 2 级\"}"
  },
  {
    "role": "assistant",
    "content": "北京今天晴间多云，气温约 24°C，湿度 48%，东北风 2 级。整体适合跑步，建议避开午后高温时段并及时补水。"
  },
  {
    "role": "user",
    "content": "那明早还是这个温度吗？"
  }
]
```

这条列表的执行过程是：

```text
system
  定义助手行为和工具使用规则

user
  用户第一次提出问题

assistant(tool_calls)
  模型决定调用 get_weather，此时还没有最终回答

tool
  后端真正执行工具，返回天气数据

assistant
  模型根据 tool 结果生成最终文字

user
  用户继续追问，历史消息一起回传
```

最关键的关系是：

```text
assistant.tool_calls[0].id
        =
tool.tool_call_id
```

本例中两边都是 `call_weather_001`。如果 ID 对不上，大多数模型接口会认为工具结果无法关联。

几个容易出错的细节：

- `assistant` 发起工具调用时，`content` 通常可以是 `null`，最终回答还没有产生。
- `function.arguments` 是 **JSON 字符串**，通常不是 JSON 对象。因此需要先解析字符串，再调用工具。
- `tool.content` 一般也是字符串；可以把查询结果序列化后放进去。
- 一个 `assistant` 可以同时请求多个 `tool_calls`，每个调用必须分别对应一条 `tool` 消息。
- `tool` 消息不能孤立出现，它必须关联前面某条 `assistant.tool_calls`。
- 工具结果属于数据，不应被视为新的系统指令。工具结果中的“忽略之前规则”等文字需要防范提示词注入。


## 什么是上下文窗口

**上下文窗口是模型单次推理能“看见”的最大 Token 数量。** 它不是数据库存储空间，也不是永久记忆。你可以把它理解为模型的短期工作记忆容量。

逻辑上分为以下七个部分：**系统指令、工具定义、长期记忆、对话历史、检索知识、用户当前问题、大模型回复**

### 系统指令和长期记忆

系统指令和长期记忆的设计目标不同：**系统指令追求“行为可预测”，长期记忆追求“信息可复用”**。两者在实现上需要分开处理，不能混为一谈。

#### 系统指令的设计

系统指令的核心问题是：如何让 Agent 在每一轮都按照同一套规则行事，不被用户输入带偏。

**结构化优于散文式。** 微软的 Agent 控制框架建议将系统指令组织为五个独立部分，每部分承担不同的控制功能：

| 部分 | 作用 | 关键写法 |
|---|---|---|
| 标识与角色 | 定义 Agent 是谁、不是什么 | 明确边界，例如“你是决策支持工具，不是自主决策者” |
| 行为约束 | 显式列出不会做的事 | 用“不会”而非“不应”，绝对化表述减少回旋余地 |
| 范围限制 | 定义可处理的主题边界 | 超出范围时明确拒绝，不尝试“尽力而为” |
| 升级触发条件 | 什么情况下停止并转人工 | 可量化条件，如“置信度低于 70%” |
| 输出格式要求 | 结构化响应的架构 | JSON schema、字段要求、引用格式 |

**约束用绝对化语言。** 微软的指南特别指出，约束应以“不会”这类表述来说明，而不是“不应”或“尽量避免”——绝对性语言减少模型将约束理解为建议而非规则的空间。

**测试驱动编写，而非凭感觉堆砌。** 先写行为测试用例，再写指令。每个测试用例包含输入、期望行为、通过标准，然后迭代修改指令直到所有用例通过。这样每条指令的存在都有测试依据，而不是“看起来合理”。

**一个实用细节：系统指令不存对话状态。** 微软明确提醒，系统消息应定义角色、范围、语气和兜底行为，而不是用来存储对话历史或用户数据——那些属于对话记录或检索数据的职责。

#### 长期记忆的设计

长期记忆的核心问题是：跨会话保留哪些信息、以什么形式保留、什么时候注入。

**分层而非单一存储。** 常见的工程实践是至少分两层：**核心记忆**和**归档记忆**。核心记忆容量有限（例如约 10 个块、2000 token 以内），始终注入上下文，存放用户画像、偏好等关键信息，按优先级淘汰；归档记忆容量不受限，但需要显式检索才能进入上下文，存放历史事实和细节。Databricks 的划分更简洁：短期记忆捕获单会话上下文，长期记忆跨会话提取关键信息用于个性化。

**更新策略要有“慢下来”的机制。** 一个容易踩的坑是：用户某次随口说的一句话被立刻写入长期记忆，导致画像被临时偏好污染。RGMem 框架的做法是：短期的日常交互先积累，只有当一致证据足够多时，才更新对用户的长期理解。它把快速变化的“证据”和缓慢变化的“特质”分开处理，避免对临时情况过度反应。学术界的 TriMem 也采用类似思路：原始对话片段、提取的原子事实、合成的用户画像三种粒度共存，而不是只存扁平的事实列表。

**注入时机与预算独立。** 长期记忆每轮只注入被检索命中的少量条目，而不是全部塞入。这意味着你需要为它设一个独立的 token 配额（比如几百 token），并定义检索触发条件（每轮都检索、还是仅在新会话首轮检索）。MemCore 的做法是：核心记忆始终注入，归档记忆仅在显式搜索时返回。

**写入时机明确规则。** 不要依赖模型“自己记住”。生产级 Agent 的常见模式是：运行开始时读取记忆文件，运行结束时写入更新；如果文件缺失则创建空白继续。写入什么、覆盖还是追加、冲突时以谁为准，都需要显式规则，而不是留给模型即兴判断。

两者的配合方式可以概括为：**系统指令是每轮固定加载的“宪法”，长期记忆是每轮按需调取的“档案”**。前者定义 Agent 永远不能做什么，后者提供 Agent 这轮需要知道什么。混在一起管理，就失去了各自独立控制的能力。

### 长期记忆和检索知识

长期记忆和检索知识在工程实现上确实很像——都是"外部存储 + 检索 + 注入上下文"，用的甚至可能是同一套向量数据库。但它们的**信息来源、更新逻辑、失效条件和注入目的**不同，这个区别决定了你该怎么设计它们。

#### 核心区别：记忆是"关于谁的"，知识是"关于什么的"

| 维度 | 长期记忆 | 检索知识（RAG） |
|---|---|---|
| 内容性质 | 关于用户/Agent 自身的事实与偏好 | 关于外部世界/领域的静态或半静态资料 |
| 来源 | 从交互中提炼（用户说过的话、行为） | 外部知识库、文档、网页、数据库 |
| 更新频率 | 随交互缓慢演化 | 随知识源更新，与交互无关 |
| 生命周期 | 跨会话持久，属于"这个用户/这个 Agent" | 只要知识源有效就有效，不属于特定用户 |
| 失效条件 | 用户偏好变了、信息过时 | 文档被修订、知识过期 |
| 注入目的 | 个性化：让回答符合"这个人" | 事实性：让回答有依据、不幻觉 |
| 检索触发 | 通常每轮或会话首轮，按用户身份 | 按当前问题语义匹配 |

一句话概括：**长期记忆回答"我知道你什么"，检索知识回答"我知道世界什么"。** 前者是主体相关的，后者是客体相关的。

#### 为什么容易混淆

因为两者在技术栈上高度重叠：都可能存在向量库里，都用相似度检索，都拼进上下文。如果你只看"存储-检索-注入"这条链路，它们长得一模一样。区别不在管道，而在**管道的上游和下游**。

- **上游**：记忆的写入源是对话本身（用户说"我偏好简洁回答"），知识的写入源是外部文档（产品手册、法规条文）。写入者不同：记忆是 Agent 自己在运行中提炼的，知识是人预先灌入或定期同步的。
- **下游**：记忆注入是为了"调整行为"（这个人喜欢什么风格、有什么约束），知识注入是为了"提供事实"（这个产品的退款政策是什么）。前者影响怎么说，后者影响说什么。

#### 设计上的实际差异

**更新策略不同。** 知识库通常是批量同步、版本管理，更新是"替换文档"；记忆是增量写入、冲突合并，更新是"修正对用户的理解"。前面提到的 RGMem 那种"证据足够多才更新特质"的慢更新机制，只适用于记忆，不适用于知识——知识文档改了就该立刻生效。

**失效与删除不同。** 知识过期是"文档下线"，可以按版本或时间戳批量处理；记忆过期是"用户偏好变了"，需要按用户维度精细管理，还涉及隐私删除（用户要求忘记某件事）。

**预算和注入频率不同。** 记忆通常是小配额、高频注入（每条请求都带用户画像）；知识是大配额、按需注入（这轮问题相关才检索，且可以截断）。把两者混在一个配额里，会导致"知识检索挤掉用户画像"或反之。

**评测方式不同。** 记忆的评测看"个性化是否到位、是否记住了该记的、是否忘了该忘的"；知识的评测看"检索召回率、答案事实准确性、引用是否可追溯"。

#### 一句话总结

它们共享"检索注入"这个技术形态，但**记忆是 Agent 对交互对象的内部表征，知识是 Agent 对外部世界的参考资料**。设计时把它们放在同一个向量库里没问题，但预算、更新、失效、评测这四条线必须分开管，否则你无法回答"这条信息该不该留、该不该信、该不该删"。

### 为什么多轮对话会越来越占空间

模型没有跨请求自动记忆，因此前端每次都要重新发送历史。历史越长，输入 token 越多，成本和延迟通常也越高。

### 窗口被占满时怎么办

常见策略有四种：

| 策略 | 做法 | 优点 | 风险 |
| --- | --- | --- | --- |
| 滑动窗口 | 删除最早的消息 | 简单、稳定 | 早期信息丢失 |
| 摘要历史 | 把旧对话压缩成摘要 | 保留部分语义 | 摘要可能遗漏细节 |
| RAG 检索 | 只检索相关资料片段 | 适合大知识库 | 检索不准会引入错误信息 |
| 压缩工具结果 | 只保留工具结果关键信息 | 减少大 JSON/网页占用 | 可能丢失必要字段 |

优先级通常是：

```text
System Prompt 必保留
本轮最新 user 消息必保留
相关工具结果必保留
近期历史优先于早期历史
旧历史再考虑摘要或丢弃
```

### 上下文窗口的几个误区

- **窗口大不等于记得好。** 内容过长时，模型可能忽略中间部分，通常称为 “lost in the middle”。
- **窗口够大也不代表成本低。** 输入 token 按次计费，每轮都重新发送历史会增加费用。
- **数据库内容不会自动进入上下文。** pgvector 只是存储向量，必须通过检索把相关片段插入消息列表。
- **temperature 不会改变上下文容量。** 它只影响采样随机性。
- **上下文窗口是工作台，不是长期记忆。** 长期会话需要应用自己持久化和恢复。

一句话概括：

```text
上下文窗口 = 模型本次推理的工作台；
消息列表 = 放到工作台上的材料；
裁剪/摘要/RAG = 工作台放不下时的整理策略。
```

## Token 数

**Token 是模型处理和计费的最小文本单元。** 它不等于字符，也不等于单词。对 Gemini 模型而言，一个 token 大致相当于 4 个英文字符，100 token 约对应 60–80 个英文单词。中文的换算关系因分词器而异，参考值约为 1 个中文字符对应 0.6 个 token，但不同模型的分词方式不同，实际数量以 API 返回的 `usage` 字段为准。

deepseek提供了离线的[tokenizer工具](https://cdn.deepseek.com/api-docs/deepseek_v4_tokenizer.zip)可以用于计算文本消耗的token

在 Agent 开发中，Token 数出现在两个关键位置：

**一是约束检查。** 每个模型都有输入加输出的 token 上限。你可以在发送请求前调用 `countTokens` 接口预估用量，避免因超限导致请求失败。这个接口本身不收费，配额通常也足够开发使用。

**二是成本归因。** Token 数是计费的基础单位。调用完成后，响应中的 `usageMetadata` 会告诉你实际的输入 token、输出 token、思考 token 各是多少。养成在 Agent 的每次调用中记录这些字段的习惯，后续做成本分析和优化时才有数据可依。

## Temperature

**Temperature 控制模型输出时选择 token 的随机程度。** 数值越低，模型越倾向于选择概率最高的 token，输出更确定、更保守；数值越高，低概率 token 被选中的机会增加，输出更多样、更有“创造性”。

对 Agent 开发，温度设置需要匹配任务类型：

| 场景类型 | 建议温度 | 理由 |
|---|---|---|
| 工具调用、结构化输出、代码生成 | 0–0.3 | 需要确定性，减少格式错误和幻觉 |
| 信息提取、问答、摘要 | 0.3–0.7 | 兼顾准确与自然表达 |
| 头脑风暴、创意写作、角色扮演 | 0.8–1.2+ | 鼓励多样性 |

Gemini 模型的温度范围是 0.0 到 2.0，默认 1.0。一个值得注意的细节：如果模型返回的回答过于笼统、简短，或者频繁给出兜底回复，适当**调高**温度可能改善；如果模型陷入无限生成循环，把温度提到至少 0.1 有时能打断循环。温度不是越低越“安全”，它需要和具体模型的特性配合调试。

在 Agent 中，一个常见模式是**分环节设温度**：规划步骤用较高温度（鼓励多角度），执行步骤用低温度（保证准确），最终回答用中等温度。

## 费用估算

**Agent 的费用 = 输入 token 费用 + 输出 token 费用（+ 缓存相关费用）。** 不同模型的输入和输出单价不同，通常输出单价是输入的数倍。以 Claude 系列为例，Sonnet 4 的输入约 $3/百万 token，输出约 $15/百万 token；Opus 系列则可达 $15/$75。

计费公式本身很简单：

> 费用 = 输入 token 数 × 输入单价 + 输出 token 数 × 输出单价

但 Agent 场景有几个容易踩坑的地方：

**缓存命中会改变单价。** 如果你使用了上下文缓存（Context Cache），命中缓存的那部分输入 token 按更低的“缓存命中”单价计费，未命中的按正常输入单价。输出部分不受缓存影响。很多模型支持这一机制，尤其是系统提示词较长、多轮对话重复前缀较多的 Agent 场景，缓存能显著降低成本。

**思考 token 需要单独关注。** 部分模型（如 Gemini 的思考模式）会在输出中产生“思考 token”，它们计入总 token 但可能以不同方式出现在 usage 字段中。做成本估算时不能只看 `candidates_token_count`，要确认 `thoughts_token_count` 是否被单独统计。

**实际估算建议用工具而非手算。** 有现成的 Python 库（如 `llm-costs`、`llmcalc`）可以直接从 API 返回的 usage 数据计算费用，并自动处理缓存命中、批处理折扣、长上下文加价等复杂规则。在 Agent 的成本监控 pipeline 里接入这类工具，比手动维护价格表更可持续。

最后一条实用原则：**先测再估**。在开发阶段用真实请求跑一遍，收集 `usage` 数据，算出单次 Agent 调用的平均 token 消耗，再乘以预估调用量。测试环境和生产环境的 token 消耗往往差距很大（如前文所述 900 vs 9,000 的例子），拍脑袋估算容易严重偏离实际。


## 为什么对话要回传历史?

对话要回传历史，根本原因是：**大模型 API 是无状态的，模型本身不记得上一轮发生了什么。** 每一次 API 调用都是一次独立的推理，服务端不会为你的会话保留任何上下文。你不把历史发过去，模型就只知道这一次的输入。

### 具体原因

**1. 模型无状态，历史是唯一的"记忆"载体**
你上一轮说"用 Go 写一个 HTTP 服务"，这一轮说"加上超时控制"。如果只发第二句，模型不知道"加上"是加在什么上面。只有把第一轮的内容一起回传，模型才能理解"加上"指的是给刚才那个 Go 服务加超时。所谓"多轮对话"，本质是客户端把整段历史重新拼进请求，让模型每次都"重新读一遍"。

**2. 保持指代和上下文连贯**
对话里大量存在"它""那个""上面说的""再改一下"这类指代和省略。这些信息不在当前这句里，只存在于历史中。不回传历史，模型无法解析指代，回答就会跑偏或反问。

**3. 让模型基于已有决策继续工作**
Agent 场景尤其明显：模型前面已经调用了工具、拿到了结果、做了推理，下一步要基于这些中间结果继续。工具返回、推理结论都在历史里，不回传就等于让模型失忆重来。这也是为什么 Agent 的 token 消耗会随轮次快速膨胀——每一轮都要把之前所有的工具调用和结果重新发一遍。

**4. 保持行为和风格一致**
历史里包含了模型之前的回答方式、已经确认过的约束、用户表达过的偏好。回传历史能让后续回答延续同样的风格和前提，而不是每次重新摸索。

### 一个关键推论

正因为历史是"客户端回传"的，**窗口管理责任在开发者这边**。模型不会自动帮你压缩或遗忘，历史只会越积越长，直到撑满上下文窗口。所以上一轮讲的滑动窗口、摘要压缩、按类别分配预算，都是在这个前提下才需要的工程手段——如果模型自己记得，这些都不必做。


## 总结

- **上下文窗口**：模型单次推理能“看见”的全部 token 上限，输入（系统指令、工具定义、记忆、检索知识、对话历史、当前问题）和本轮输出都挤在这一个固定容量里。
- **Token 数**：模型处理和计费的最小文本单元，不等于字符或单词，实际用量以 API 返回的 usage 字段为准。
- **Temperature**：控制模型选词随机程度的参数，低值偏确定保守、高值偏多样发散，需按任务类型（工具调用/问答/创意）分别设置。
- **费用估算**：用输入 token 数×输入单价 + 输出 token 数×输出单价（再叠加缓存命中折扣或写入溢价）来预估单次调用成本，建议先用真实请求测 usage 再外推。
