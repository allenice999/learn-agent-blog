# SSE 事件协议设计

## SSE 消息格式

```typescript
export type SSEEventName =
  | "token"          // 流式文本增量
  | "message"        // 完整消息（落库后）
  | "tool_start"     // 工具开始执行
  | "tool_result"    // 工具执行完成
  | "interrupt"      // 人工审批中断（W5/W6 用，D1 占位）
  | "done"           // 本轮结束
  | "error";         // 错误
```

1. token 和 message 分开

token 高频（每字一次），只用于渲染；message 低频（每轮一次），带 messageId 用于落库对齐和前端历史加载。如果只有 token，W5 调试时前端无法区分“这条消息是否已持久化”。

2. tool_start / tool_result 靠 callId 配对

Agent 可能并行调多个工具，前端需要把“开始”和“完成”配成同一张卡片。没有 callId，多个工具调用会串。真实 Agent SSE 契约中同样强制 tool_result 必须跟随其对应的 tool_call 。

3. riskLevel 放在 tool_start 里

W6 审批弹层的触发条件是“高危工具”，但前端在 tool_start 时就需要知道是否要准备弹窗（或者至少渲染一个“待审批”状态）。interrupt 事件是后端真正暂停时推的，但 riskLevel 提前告知能让 UI 更早准备。

4. interrupt 事件独立于 tool_start

LangGraph 的 interrupt 是图层面的暂停，可能发生在工具执行之前（审批后才执行），也可能发生在中间步骤。它携带的 actionRequests 可能包含多个待审操作，所以不能复用 tool_start 的载荷结构。参考 LangGraph 的 HumanInterrupt 设计：包含 action_request（名称+参数）、config（allow_accept/reject/edit）、description 。

5. done 必须最后、且只有一个

真实 Agent 契约的硬性约束：每轮恰好一个终止事件（done 或 error），且必须是最后一个 。前端据此判断“本轮结束”，重置 loading 状态。

6. error 是独立事件，不是 HTTP 状态码

流式响应一旦发出 200，后续错误只能用事件通道报告。前端需要在 error 事件中拿到 code 和 message 做用户提示，而不是白屏。

## SSE vs WebSocket

Agent对话中，有中途打断和人工审批等双向的需求

“中途打断”有两种含义

第一种：用户点“停止生成”。前端想告诉后端“别推了”。SSE 是单向的，前端关掉连接，后端通常能感知到 disconnect，但这个信号是二进制的、不可靠的。生产环境中，关闭连接可能被误判为网络故障，也可能因为负载均衡导致取消请求落到另一台机器上，后端继续跑、继续计费。如果你用 SSE，这个“停止”是尽力而为，不是可靠指令。

第二种：Agent 执行中途需要人工介入。LangGraph 的 interrupt() 机制本质是：图执行到断点挂起并持久化状态，前端收到一个“待审批”事件，用户点“批准”后，通过一个独立的 HTTP POST 请求把 Command(resume=...) 发回后端，图从断点继续。这个恢复信号根本不走 SSE 流，它走的是普通 HTTP API。

总结：选择 SSE 还是 WebSocket，主要看 SSE 是否能够满足需求，如果可以满足则优先使用 SSE，否则使用WebSocket

## 客户端发送指令怎么回传到SSE

SSE 配合 HTTP POST 实现了服务器推送流消息，但是对于添加负载均衡的服务，如果处理不好，POST 请求被转发到了实例 B，而用户的 SSE 连接挂在实例 A 上，实例 B 根本找不到那个 SSE 连接，控制就会失效

核心思路：让控制指令“找到”对应的 SSE 连接

要让 POST 指令生效，必须确保处理指令的后端代码能访问到代表 SSE 连接的对象。在单机环境下，用一个 Map 存起来就行；

在多实例加负载均衡的环境下，需要额外机制来保证这一点。

常见的做法有以下几种：

1. 会话粘性（Sticky Session）

这是最直接的方式。配置负载均衡器（如 Nginx），让来自同一个客户端的请求（包括 SSE 的 GET 和控制用的 POST）始终被转发到同一个后端实例。

优点：后端代码最简单，连接对象就在本地内存里。

缺点：牺牲了负载均衡的灵活性。如果该实例挂了，用户的 SSE 连接和控制能力都会中断。某些负载均衡器可能不支持或不方便配置基于 Cookie 的粘性。

2. 共享存储（如 Redis）

用一个外部存储来记录“哪个用户的 SSE 连接在哪个实例上”。

当 SSE 连接建立时，实例 A 向 Redis 写入一条记录：用户ID -> 实例A。

当 POST 控制请求到达（可能落在实例 B），实例 B 先查 Redis，发现该用户的连接在实例 A，然后通过内部通信（如 Redis Pub/Sub 或 RPC）通知实例 A：“请向这个连接发送控制指令”。

优点：解耦了实例，负载均衡可以自由调度。

缺点：引入了外部依赖（Redis），增加了架构复杂度和延迟。

3. 消息队列路由（如 RabbitMQ）

每个 SSE 实例在启动时，向消息队列（如 RabbitMQ）创建一个独占队列。当用户连接时，在该队列上绑定一个以用户 ID 为路由键的绑定。控制指令通过消息队列的交换机发出，由消息队列负责将其路由到持有该用户连接的那个实例的队列中。

优点：利用成熟的消息中间件，路由逻辑清晰，可靠性较高。

缺点：同样引入了额外的基础设施。

---


结合 Agent 场景的实践建议

对于 Agent 应用，如果选择“POST + SSE”方案，我建议采用 “共享存储 + 内部广播” 的模式，因为它最灵活：

建立连接：前端通过 GET 请求建立 SSE 流。后端实例 A 生成一个唯一的 streamId，连同用户 ID 一起存入 Redis，并将 SseEmitter 对象保存在实例 A 的本地 Map 中。

发送指令：前端发送 POST /cancel 或 POST /input 请求，携带 streamId。假设请求被负载均衡到实例 B。

路由指令：实例 B 查询 Redis，得知 streamId 对应的连接在实例 A。实例 B 通过 Redis Pub/Sub 向实例 A 发送一条消息：“请对 streamId 执行取消操作”。

执行控制：实例 A 收到内部消息后，从本地 Map 中找到 SseEmitter，执行相应的控制逻辑（如终止生成任务、发送中断信号）。

## 为什么事件分 6 类

token(流式增量) / message(完整落库消息) / tool_start / tool_result / done / error。


- token 和 message 分开：token 高频、只用于渲染；message 低频、含 messageId，用于落库对齐。
- tool_start/tool_result 靠 callId 配对：前端把两者配成一张工具卡片，没有 id 配不上。

## 什么有 riskLevel

审批弹层靠它决定是否弹窗。

## 为什么 done 带 usage

评测要算成本。

## 为什么 error 是独立事件而非 HTTP 状态码

流已开始（200 已发）后出错，只能用事件通道报错；前端要能兜底不白屏。
